# v2.9.4 — Bound background memory and pass waits

Cold preparation builds a day's forecast fold from completed quarter-day folds when they cover exactly the same source files.
This reduces the rows retained by the ordered aggregate without changing its winner selection.
Missing, incomplete, or extra-source quarter folds fall back to the original copies.
Existing incremental updates and atomic publication remain unchanged.
An 83-file public snapshot reproduced a DuckDB memory-limit failure while constructing a cold day fold.
Reusing its completed quarters allowed that remaining preparation step to finish under the unchanged 1536 MB limit.

Cache warming builds one weather view or forecast detail at a time.
Each background build runs its component queries sequentially, reducing simultaneous query working sets.
Interactive cache misses retain their parallel query path and existing deadlines.

A stale forecast detail, weather view, or observation aggregate that a reader finds is rebuilt in the background only when a heavy-work turn is free at that moment.
Without one, the reader receives the cached value and a later reader retries; refreshes never queue ahead of processing, file preparation, or waiting requests.
A refresh skips its rebuild when warming has already refreshed the value.
The station list, refreshed one at a time, waits for its turn like cache warming.

DuckDB results stream to the decoder instead of being materialized first, and decoding consumes one batch at a time.
A DuckDB error raised while results are being read returns a query error instead of failing the task.

File preparation takes exclusive heavy-work admission for each copy and again for folding, releasing it in between.
A processing pass waiting behind preparation runs after the step under way rather than after every pending copy.
After admission, a processing pass takes the processing lease again and skips if another process holds it.
If a lease renewal finds another holder, the pass stops between events.
`oracle_pass_admission_wait_seconds{pass}` reports how long processing, file preparation, and eligibility reading have waited for exclusive admission.

Sequential warming can take longer; monitor warming duration, data freshness, and heavy-route latency after deployment.
DuckDB allocations and foreground query concurrency remain possible sources of memory peaks.
These changes do not impose a complete process-memory cap.

This release also aligns Nix package and Helm application versions.
The v2.9.3 publication stopped at version validation; its signed tag remains unchanged.
Pull request CI now runs the same version validator as release publication.
